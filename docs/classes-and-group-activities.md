# Classes and group activities — October 22, 2026

Implementation for review on `feature/classes-group-activities`, based on the released `42bd55d` tree. This has not been applied to production. The earlier release authorization covered the field cleanup; this feature requires its own migration/release decision.

## One connected workflow

Classes is the reusable child-group directory. Each class has one branch, an active/archive state, a named child roster and suggested staff. Children can belong to more than one scheduling class; this is not effective-dated room enrollment. Existing staff `care_groups` stays separate and no memberships are converted or guessed.

A manager opens Schedule from a class card, reviews the copied roster, selects one or more assigned staff and sets an activity name/type/time/location. The activity is saved once, with child and staff name/identity snapshots. Class edits or archiving never silently update saved activities. A stale class version is rejected, with an explicit reload/review action. The first version fixes the participant roster when scheduled; changing a saved roster requires canceling and creating a reviewed replacement. Time, location and cancellation edits are version checked and audited.

The same group event appears in the scheduling list, the shared activity workspace, every assigned worker's daily work, the Home calendar and daily totals, child profile links and the D3 report/CSV. It counts once as an event, not once per child or worker. Canceled group activities appear in assigned-work history, separately from the existing paginated clinical/individual history. Existing single-child activities continue to use their existing records and workspace. Group activities do not create per-child clinical sessions or use therapeutic execution/completion or clinical notes.

The shared scheduling navigation is now Schedule. The existing Childcare vocabulary preset already supplies Activity/Activities and My Activities; no vocabulary or clinical enablement setting is changed automatically. Existing clinical terminology/access remains separately enforced. All new text fields follow the approved plain-field style.

## Storage, authority and compatibility

The additive migration is `20261022044100_classes_group_activities.sql`, generated by the installed Supabase CLI. It introduces private, RPC-only class rosters, group events, participant snapshots and append-only revision history. All seven new tables have RLS, authenticated direct access revoked, composite tenant foreign keys and lookup indexes. Public wrappers are invoker functions; private implementations have empty search paths, explicit actor/tenant/device checks and anonymous execution revoked. No existing applied migration is edited.

Class roster administration reuses existing child-management authority. Scheduling managers can read class choices and create/edit group activities. Each assigned staff member can read that activity's minimal participant roster; this does not grant full child-profile, clinical, attendance, report or class-administration access. Inactive/foreign/out-of-branch children and inactive/non-frontline/foreign staff are rejected for new scheduling. The branch is an explicit recorded scheduling branch; it does not imply staff attendance or attendance scopes.

Group creation shares the existing opaque-operation receipts, organization lock and cancellation fence. Browser storage still contains only an actor/org-scoped operation UUID. Identical retries return the same event; changed-payload retries and canceled operations are rejected. Class version and schedule versions reject stale saves. Class/event audit history retains server-derived actors and versions.

`activity_schedule` delegates individual reads to the preserved original implementation and serves group reads through the same workspace contract. Calendar/group list failures surface as errors rather than silently reporting incomplete totals. D3 remains an invoker endpoint: its added group source independently requires both report and schedule authority. Single-child records still use current child-branch membership; group events use their explicitly recorded branch. Dates retain existing device-local scheduling and organization-timezone report semantics.

No subscription/pricing, attendance, employee timekeeping, clinical entitlement, guardian/pickup, capacity, licensing-ratio or classroom presence behavior is introduced. The feature registry continues to distinguish reusable grouping from the blocked formal classroom foundation.

## Release procedure

After approval, inspect current production migration history and reconcile the existing local/remote version differences. Apply only this new forward migration, then run database advisors and scoped read-only checks before deploying the group-aware application. The migration creates no customer groups or activities and changes no customer settings/grants.

Keep the group-aware read paths when rolling back or forward-fix them: an old application would hide the new group events. Never delete group records, snapshots, audit history, receipts, cancellation fences or rewrite clinical records to support an older UI. Verify fresh required CI and tenant/device/subscription behavior before release.
