## Attendance

`/attendance` is a dedicated branch-level presence workspace. It records server-confirmed check-in/out, shows open visits even when they began on an older date, offers reasoned corrections/voids and preserves immutable revision history. Current branch membership is used to choose a child for a new check-in; historical reads and checkout use the visit's recorded branch. Deactivated children/branches can still have an authorized existing visit closed. The interface always says classroom is not recorded and makes no pickup, workforce or ratio claim.

The new independent grants are View attendance, Record attendance and Correct attendance. Nonowners start with all three false. View is required for recording/correcting; record and correct do not imply one another. Correction authority remains owner/admin-controlled. Existing Manage users, delegation, self/owner/admin protections still apply. Attendance branch assignments have their own owner/admin user-management surface and history, separate from staff locations/care teams. An admin with user-management authority may administer scopes without gaining attendance reads. Owners follow the existing explicit owner authority model.

Private source/projection/operation tables have RLS enabled and no ordinary direct table privileges. The narrowly elevated RPCs derive organization/actor from current authenticated state, require an unlocked valid device/account, verify tenant relationships and recheck branch/action authority. Organization then child locks serialize writers and scope changes; the current projection also has a unique open-visit constraint. Matching operation IDs return the original committed result only after current authorization checks. Different payload/actor reuse conflicts. Correction versions reject stale editors, and all effective intervals for a child are checked for overlap.

Corrections keep both the original and replacement check-in dates within today plus six preceding dates in the captured IANA timezone, reject future/invalid/overlapping intervals and require a staff-only reason. The UI accepts explicit UTC timestamps ending in Z rather than silently resolving ambiguous/nonexistent local times. Original events are never overwritten. Voids remain discoverable in historical views for correctors; they are excluded from presence exports. Correctors need scope over all branches represented in full history. No automatic midnight checkout or purge exists.

A record-specific continuation permits server-time checkout for an eligible visit opened while editing was permitted and before the current subscription deadline. It retains current record/branch/device/account authority and permits no new visit, reopen or historical correction during read-only access. It does not reuse the clinical-session exception. Interrupted saves retain their operation ID when unchanged details are retried; no optimistic success is displayed.

Attendance reads use the explicit organization reporting timezone introduced in slice 2. Open-only mode intentionally ignores the chosen date range so old unresolved visits stay visible. Date mode selects visits overlapping the half-open local range. Each page/export is a fresh independent snapshot with a maximum of 100 visits; child choices are limited to 100 matches and can be narrowed by name. Exports require report access in addition to attendance view/scope and include filter/timezone/generation context, formula-safe cells and no correction reasons. As in slice 2, authorized reads are not a promise that data cannot be copied by its viewer.

## Searchable saved choices and recent details

Session creation now searches existing child/staff/type/location choices instead of requiring long select lists. Recently successful selections are prioritized. Unknown children/staff still use their separately authorized People workflow; scheduling permission cannot create accounts or client records. New activity types have an explicit duration and create/save action, with normalized-name deduplication and conflict handling for differing existing durations. Location choices can be explicitly saved without creating an attendance branch or classroom.

Location search also includes previously entered locations in the already-authorized loaded session list. Those historical strings remain custom scheduling labels; choosing one never reactivates a retired branch. Current child/provider/type references and saved tags are checked before reuse, and the existing creation RPC still validates provider/client and session prerequisites. The reusable-context wrapper retains that RPC's clinical preparation behavior for compatibility with existing organizations.

The server stores at most ten recent successful detail sets per user/organization: current child/provider/type references, scheduling location, duration and selected tag IDs. It stores no old session date, note or clinical measurement in those presets. Recent details are never shared across users. Selecting a suggestion is explicit; it populates details and may suggest an end from the entered start plus duration, but never creates a session or copies an old date. Typed text is not saved until a create/save action is selected.

Session creation, selected tag snapshots, recent choices and the operation receipt commit atomically. Retrying unchanged creation details uses the same operation ID rather than creating a duplicate session. The original untagged creation RPC remains available to existing clients; no existing sessions are rewritten or backfilled.

## Shared tags versus ABA add-on work

The reusable tag engine is a **shared/base** feature. A saved tag has a separate shared/daycare/client-care/ABA category; that metadata describes intended context and backlog ownership, not enabled entitlements or diagnoses attached to children. No product gate, price, profile-based access change or compliance assertion is introduced.

Examples are suggestions, not automatically created defaults: “Outdoor play” can be daycare context; “Parent observed” or “Parent-led practice” can be ABA/client-care context. Labels are optional. They record a user's chosen session context and do not prove parent identity, consent, training, competency, home practice or treatment progress. A saved label is not a guardian relationship or pickup authority. Session managers can see creation-time tag snapshots on the session administration page; renaming a future reusable choice cannot rewrite that snapshot.

Verified caregiver training, parent competency checklists, structured supervision, measurement-aware capture and treatment outcomes remain separate clinical add-on work. The feature registry marks parent context partial for this reason; it does not mislabel simple tagging as a completed clinical workflow. D4 remains blocked as a complete report because classrooms/absence models are missing; the implemented branch-presence view is explicitly narrower. D6/D7 and guardian/daily-care features remain blocked.

## Release and verification

Apply slice 2's two migrations first, then `20261018084149_branch_attendance.sql` and `20261018084157_session_context_tags.sql`, before deploying this code. New permissions default false; do not bulk-enable them or infer branch scopes from existing care assignments. The account editor, effective capability navigation and new RPCs depend on those columns/functions. Retention/archival decisions remain a production rollout prerequisite from the approved proposal. An app rollback must not delete attendance history, saved labels or tag snapshots.

Database tests exercise real role/tenant/device boundaries, private table denial, scope changes, history immutability, stale versions, retries, inactive-record checkout, read-only continuity, old/overlapping corrections, DST boundaries, tag/type normalization, wrong-kind/unknown tag denial and per-user recent history. An independent-connection PostgreSQL test races distinct check-ins, identical checkout retries and competing corrections. The synthetic browser flow covers interrupted check-in retry, correction/history, CSV minimization, mobile layout, explicit type/location/tag creation, parent context and recent reuse without dates. Original device, invitation, permission, calendar, setup and clinical-program tests remain relevant regression checks.

For offline tests, use the existing `REJOYCE_BASELINE_SQL` and `REJOYCE_PGLITE_MODULE` variables. The concurrency test additionally requires `REJOYCE_POSTGRES_CLIENT` pointing to the `postgres` JavaScript client and an isolated PostgreSQL server on **127.0.0.1:55439**, accessible as local `postgres`. It creates/drops only its own synthetic `attendance_test_<pid>` database; never point it at production. The browser runner uses `PLAYWRIGHT_MODULE`, a local app with synthetic `https://workflow-test.supabase.co` configuration, and intercepts HTTP RPC calls into the isolated database fixture. Temporary test binaries are kept under ignored `work/`, not added to application dependencies.

Verified locally: all 140 regression tests pass, including the independent PostgreSQL concurrency tests. The optimized production build and the synthetic attendance/session-context browser flow against that build pass. No production database or deployment was changed.
